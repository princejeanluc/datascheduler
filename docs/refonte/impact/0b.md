# Note d'impact : lot 0b — `ui/time_display.py` et conversion des heures affichées

## Ce que le lot change
- Nouveau module `ui/time_display.py` :
  - `to_display(dt_utc)` — convertit un instant UTC naïf vers `AppSettings.timezone` (relu à
    chaque appel via `db.get_app_settings()`, pas de cache), renvoie un naïf prêt à formater.
  - `fmt_time(dt_utc, fmt="%H:%M:%S")` / `fmt_datetime(dt_utc, fmt="%d/%m/%Y %H:%M")` —
    convertissent puis formatent. Le paramètre `fmt` optionnel n'est pas dans l'esquisse de
    `FONDATIONS.md` ; il est nécessaire pour migrer tous les sites listés ci-dessous **sans
    changer la précision déjà affichée par chacun** — le code actuel mélange déjà `%H:%M:%S` et
    `%H:%M`, `%d/%m/%Y %H:%M:%S` et `%d/%m/%Y %H:%M` selon l'écran ; centraliser la conversion
    n'est pas une occasion de les uniformiser sans que la fiche le demande (REGLES.md section 1).
  - `fmt_time_local(dt, fmt="%H:%M")` / `fmt_datetime_local(dt, fmt="%d/%m/%Y %H:%M")` — même
    principe, sans conversion : la variante pour `Pipeline.next_run_at` et `expected_at` (sa copie
    dans les dialogues de rattrapage), déjà dans le fuseau réglé.
  - `fmt_relative(dt_utc)` — « il y a 45s » / « il y a 4 min » / « il y a 2 h » / « il y a 3
    jours », généralisation des deux idiomes dupliqués existants (`settings_view.py` en
    secondes, `connections_view.py` en jours) ; la sortie reproduit exactement leur texte actuel
    dans leurs plages respectives (secondes, jours), les paliers minutes/heures sont nouveaux
    (aucun site actuel ne les utilise).
- Les 14 sites recensés (8 à convertir, 4 déjà locaux, 2 relatifs — liste ci-dessous) remplacent
  leur `strftime` direct. `activity_chart.py`, `history_view.py:255` (en-tête de jour) et
  `widgets.py` (infobulle de la heatmap) restent hors périmètre : ce sont des agrégats par date
  (sans heure), rien à convertir.
- Test ajouté conforme à `FONDATIONS.md` section 4 : un run à 05:00 UTC s'affiche 07:00 avec
  `Europe/Paris` en été.

actuel à l'identique.

## Risques et retour arrière
Risque principal : un utilisateur dont le fuseau réglé diffère d'UTC verra les heures de ses
runs passés *changer visuellement* (elles s'affichaient en UTC, elles s'afficheront dans son
fuseau) — c'est le défaut corrigé, pas une régression, à mentionner dans la PR. Un appel à
`fmt_time`/`fmt_datetime` sans base de données initialisée lèverait une erreur (comme tout appel
à `db.get_app_settings()`) — vérifié que tous les écrans touchés sont déjà testés avec la
fixture `test_db` quand ils affichent un run réel. Retour arrière : revert du commit, aucune
donnée stockée n'est touchée.
